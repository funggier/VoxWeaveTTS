# VoxWeaveTTS v0.12.3 — คิวเตรียมข้อความและคิวเสียงรอเล่นแบบแยกขั้นตอน

**Windows x64 Core Portable ZIP ครบชุด** · Universal `.vwmodel` **Format V4 เท่านั้น** · ติดตั้งโมเดลออฟไลน์ได้ · **ไม่รวมโมเดลเสียงใน Core**

## เพิ่ม Live Pipeline (เปิด/ปิดได้แยกแต่ละโหมด)

เพิ่มสวิตช์ **เตรียมและสร้างเสียงข้อความถัดไปล่วงหน้า** ในหน้าตั้งค่าคิวของ YouTube LIVE (API), YouTube Browser, TikTok Browser/Extension, TikTok, Discord Bot และ Discord Client

**ค่าเริ่มต้นปิด** เพื่อคงพฤติกรรม FIFO แบบเดิม หากเปิดจะจัดงานเป็น 4 ขั้น:
1. **ข้อความจากแชท**: ข้อความดิบที่ยังรอประมวลผล รับตามลำดับเดิม ระบบสุ่มลดคิวยังคงใช้ได้ **เฉพาะขั้นนี้** ไม่สุ่มลบเสียง/ข้อความที่เริ่มเตรียมแล้ว
2. **เตรียมข้อความ**: กรอง/แทนคำ → กฎก่อนแปล → ตรวจภาษา/แปลตามตั้งค่า (รวม Ollama) → กฎหลังแปล → แบ่งภาษาตาม Engine → ข้อความพร้อมสร้างเสียง
3. **สร้างเสียงล่วงหน้า**: ปล่อยงานจากขั้นเตรียมไปยัง Worker TTS ตามช่องว่างที่จำกัดไว้ ขณะที่เสียงก่อนหน้ากำลังเล่นอยู่ได้
4. **เสียงสร้างเสร็จ รอเล่น**: เก็บ WAV ที่เสร็จแล้ว รอถึงลำดับ FIFO ของตนเองก่อนเล่น และย้ายไปประวัติอ่านแล้วเมื่อเล่นจบจริง

**คิวเสียงที่รออ่านไม่ได้บังคับให้เล่นพร้อมกัน**: ยังใช้ Global Playback Scheduler เช่นเดิม (อนุญาตให้ซ้อนเสียงได้เฉพาะกรณีเปิดตัวเลือกซ้อนเสียงที่มีอยู่)

## ตัวเลขกำหนดจำนวนคิว

อยู่ใต้สวิตช์ Pipeline ในแต่ละโหมด Live:
- **เตรียมข้อความล่วงหน้า**: ตั้งได้ **1–8 คิว** (ค่าเริ่มต้น **3**) — นับข้อความที่กำลังแปล/แยก หรือแปล/แยกเสร็จแต่รอส่งเข้า TTS
- **เสียงพร้อมรออ่าน**: ตั้งได้ **1–8 คิว** (ค่าเริ่มต้น **2**) — จองช่องรวมงานกำลังสร้าง WAV และ WAV ที่เสร็จแล้วกำลังรอเล่น เพื่อไม่ให้สร้างเกินจำนวนที่อนุญาต
- **รวมสองค่าได้สูงสุด 10 คิว** ในแต่ละโหมด เพื่อจำกัดจำนวนงานค้างหน่วยความจำ ไม่รวม WAV ของข้อความที่กำลังเล่นอยู่
- คิว **แชทดิบ** นับแยก มีตัวเลือกสุ่มลดเมื่อคิวสะสมมากเหมือนเดิม ไม่ใช้เพดานของ Pipeline
- เปลี่ยนค่าระหว่างทำงานได้ โดยไม่ลบงานที่รับเข้าประมวลผลไปแล้ว ค่าที่ปรับจะจำกัดงานใหม่
- **บันทึกการตั้งค่าคิว** ของแต่ละโหมดเพื่อเก็บสวิตช์และตัวเลขลงเครื่อง แยกอิสระระหว่างโหมด โดยไม่บันทึก Credentials

ตัวติดตั้งอ่านค่า `source-queues.json` จาก Core รุ่นเก่าได้โดยเพิ่มค่าสวิตช์ปิดและตัวเลขเริ่มต้นให้อัตโนมัติ ไม่ต้องลบหรือ Reset การตั้งค่าเดิม

## การรับมือกับคิว/ข้อผิดพลาด

- ตรวจลำดับรับข้อความก่อนแปล สร้างเสียง และเล่นเสียงเสมอ งานที่เสร็จเร็วกว่าข้ามคิวไม่ได้
- คิวเตรียมที่ผ่าน AI แล้วรอช่องสร้างเสียงจะอยู่ในสถานะ **prepared** ไม่เริ่ม TTS จน Browser อนุญาตผ่าน API เฉพาะ
- หากคิวสร้างเสียงกลางของโปรแกรมเต็ม งานเตรียมใหม่จะหน่วงรอเพื่อรับเข้าคิวแทนการทิ้งข้อความทันที โดยมีเพดานการรอ
- งานเสียงที่สร้างสำเร็จจะ **ไม่ถูกขับออกจากแคชของเซิร์ฟเวอร์ก่อน Browser ดาวน์โหลด WAV แล้ว** หลังรับไฟล์แล้ว Browser แจ้งว่าปลดการคุ้มครองแคชได้
- รีเซ็ตเฉพาะคิวรอ: ยกเลิกงานที่ยังไม่ได้เล่น แต่ไม่ขัดจังหวะข้อความที่เล่นอยู่
- สลับโหมด/หยุด: เพิกถอนงานที่ไม่ได้เล่น ป้องกันผลจาก Worker รุ่นเก่าหลุดไปเล่นในโหมดใหม่
- ปิด Pipeline ระหว่างทำงาน: งานที่เริ่มไปแล้วคงลำดับเดิม การสร้างงานล่วงหน้าใหม่หยุด และกลับไปอ่านแบบเก่าเมื่อคิวที่เตรียมแล้วหมด
- เมื่อสร้างเสียงบางช่วงไม่สำเร็จ ยังคงใช้นโยบาย **อ่านต่อเมื่อสร้างมีเสียงผิดพลาด** และพัก/ข้ามคิวตามตัวเลือกเดิม
- ข้อความหลังแปลที่ส่งเข้าโมเดลยังเป็นข้อมูล Private: แสดงผ่าน HTTP POST แบบ same-origin/intent เท่านั้น ไม่ส่งผ่าน Public Job Status, SSE หรือ Subtitle

## หน้าต่างแสดงผลในแต่ละโหมด

- **ข้อความจากแชท** — คิวแชทดิบ พร้อมระบบสุ่มลบเดิมและสถานะ
- **ข้อความที่ผ่านการแปล/แยกแล้ว · รอสร้างเสียง** — แสดงข้อความสุดท้ายที่จะส่งเข้าโมเดล (และ Engine/ภาษาแยกช่วง) หรือสถานะกำลังเตรียม
- **เสียงที่สร้างเสร็จแล้ว · รอเล่นตามคิว** — คิว WAV ที่รอเล่น (ไม่แสดงเสียงปัจจุบันซ้ำ)
- **ข้อความที่อ่านแล้ว** — เก็บเมื่อ WAV เล่นจบ ตามจำนวนประวัติที่ตั้งไว้
- **ข้อความที่ส่งเข้าโมเดลเสียงจริง** — ประวัติแบ่งช่วงหลังแปล/แทนคำ ที่มีอยู่เดิม

ปรับข้อความสถานะพร้อมรับจาก **TikTok Extension และ YouTube Browser** ให้แสดงเพียง **“กำลังรับข้อความ”** ลดข้อความซ้ำกับชื่อโหมด ขณะที่รายละเอียดการเชื่อมต่อยังอยู่ในรายการวินิจฉัย
