# VoxWeaveTTS — สถานะหน้า Browser เมื่อเลือกประมวลผลบนคอม (Core)

## หลักการ

เมื่อเลือก **รูปแบบการทำงาน → บนคอมพิวเตอร์** การรับแชทจาก YouTube LIVE (API/Browser), Discord, Discord Client, TikTok LIVE (Extension) และ TikFinity (WebSocket ภายในเครื่อง) ที่เป็น Source Manager ของ Core จะถูกอ่าน จัดคิว แปล เตรียมเสียง และเล่นเสียงโดย **Core Server เป็นเจ้าของเพียงรายเดียว**

- ทุกครั้งที่เปิดหรือรีเฟรชหน้า Browser โปรแกรมอ่านโหมดปัจจุบันและแท็บล่าสุดจาก Server แบบ **read-only** ก่อน ไม่สั่งเปิด Studio ใหม่ ไม่เริ่ม TTS และไม่สร้าง Source Session ซ้ำเอง แม้ Core จะตอบช้าหรือติดต่อไม่ได้ ก็จะไม่สั่งเปลี่ยนแท็บอัตโนมัติ
- หน้า Browser แสดงรายการข้อความต้นทางที่ยังรออยู่ งานที่ Core รับไว้ ขั้นตอนการแปล/แยก/สร้างเสียง เสียงที่พร้อมเล่น สถานะผิดพลาด และประวัติที่เล่นจบจริง แยกตาม Live Workspace
- แสดง **ผลแปล/ข้อความที่ส่งเข้า TTS จริง** เฉพาะเมื่อมีหลักฐาน Model Inputs จาก SpeechCoordinator; ขณะเตรียม/แปลยังไม่สำเร็จจะขึ้นสถานะรอแทน ไม่เอาข้อความแชทดิบมาแสดงเป็นผลแปล
- ประวัติอยู่ในหน่วยความจำ Core จึง **คงอยู่หลังรีเฟรช Browser และเปิดหน้าต่างใหม่** แต่ **ไม่ได้บันทึกถาวรข้ามการปิด/รีสตาร์ต Server**; เก็บไม่เกิน 120 ข้อความล่าสุดต่อแหล่ง และแสดงข้อความล่าสุดไม่เกิน 80 รายการเพื่อไม่ให้ DOM หนัก
- คิวที่ยังรอใน SourceManager และคิวรอส่งเข้า TTS ของ Core แสดงจำนวนจริงแยกกัน ไม่สร้างงานใหม่เพื่อแสดงสถานะ
- หน้าแรกแสดงเวอร์ชันจริงของ Server และแถบสถานะ Core รวมถึงเมื่อเชื่อมต่อไม่สำเร็จจะบอกว่าข้อมูลอาจล้าสมัย แทนแสดง 0 ผิด ๆ

## การอัปเดตโดยไม่สร้างลูปใหม่

หน้า Core Dashboard **ไม่ได้สร้าง setInterval, EventSource หรือ Worker ใหม่** ใช้ผลจากวงรอบ GET `/v1/runtime/state` ที่หน้า Settings มีอยู่แล้วเป็นสัญญาณ เมื่อ cursor ของคิว/แหล่งแชท/งานเสียงเปลี่ยน จึง POST เพื่ออ่านรายละเอียดผ่าน `/v1/runtime/dashboard` เพียงครั้งเดียวต่อ cursor โดยไม่ซ้อนการร้องขอ

ข้อมูลข้อความแชทดิบและ Model Inputs เป็นข้อมูลส่วนตัว จึงไม่ถูกส่งผ่าน GET สถานะทั่วไปหรือ SSE แต่จำกัดให้เรียกผ่าน POST แบบ **same-origin + explicit intent + การยืนยันตัวตนของ Web Control** เท่านั้น หน้า Browser ไม่เรียก `/v1/sources/drain` ในโหมด Computer และ API Server ก็ป้องกันการดึงข้อความออกจากคิวโดย Browser ในโหมดนี้อยู่แล้ว

เมื่อ Browser อยู่เบื้องหลัง จะลดการอัปเดตหน้าจอ และเมื่อกลับมาโฟกัสจะขอสถานะล่าสุดตามวงรอบเดิมโดยไม่มีการเล่นเสียงย้อนหลังซ้ำ

## ความหมายของปุ่มหยุดบน Core

- **หยุดเสียงและพักคิว Core:** ยุติเสียงปัจจุบันและพักการส่งงานจากคิว ไม่เริ่มเสียงใหม่จนกด **อ่านอัตโนมัติต่อ** หากกดหยุดในช่วงกำลังส่งคำขอเข้าระบบ งานที่ตอบกลับมาช้าจะถูกยกเลิก และเก็บข้อความที่ยังไม่ผ่านเข้าคิวไว้สำหรับ Resume โดยไม่สร้างเสียงซ้ำเอง
- **หยุดรับข้อความเฉพาะโหมด:** ปิดการเชื่อมต่อต้นทางของโหมดนั้น ยกเลิกงานเสียงและข้อความค้างของโหมดนั้น โดยไม่กระทบโหมดอื่น สามารถกดหยุดจากหน้า Browser ที่เพิ่งรีเฟรชได้ และจะไม่กลับมาเชื่อมต่อเองจนกดเชื่อมต่อใหม่
- ระบบการยกเลิกงาน AI ที่กำลังประมวลผลอาจรอให้ Worker ปล่อยทรัพยากรเดิม แต่ผลลัพธ์หลังหยุดจะไม่ถูกนำไปอ่านเสียง และไม่มีการนับเสียงที่หยุดว่าอ่านจบ

## ขอบเขตของโหมด Browser

หากเลือกโหมดที่ **Browser เป็นเจ้าของการเล่นเสียงเอง** รายการที่อยู่เฉพาะในความจำของหน้านั้นไม่สามารถรับรองการกู้คืนหลังรีเฟรชได้ โปรแกรมแสดงข้อความอธิบายนี้ในสถานะกลาง แทนหลอกว่าข้อมูล 0 เป็นข้อมูลจาก Core

**TikTok LIVE (TikFinity)** เมื่อเปิดโหมด Computer, Core จะเชื่อมต่อ TikFinity Desktop ที่ `ws://127.0.0.1:21213/` โดยตรง และเก็บคิว/สถานะอยู่ที่ Server ทำให้การรีเฟรช Browser ไม่ตัดการเชื่อมต่อ หาก Socket หลุดชั่วคราว Core จะลองเชื่อมต่อใหม่โดยไม่ต้องเปิด Browser แต่ถ้าผู้ใช้สั่งหยุด จะไม่เชื่อมต่อกลับเอง หากตั้งโหมด Browser เองจึงใช้ WebSocket ของ Browser แบบเดิมเป็นโหมดสำรอง ต้องให้ TikFinity Desktop อยู่เครื่องเดียวกับ Core และเปิดพอร์ตภายในเครื่อง 21213

การตั้งค่าที่บันทึกไว้ เช่น เสียงแต่ละโหมด กฎการอ่าน และการตั้งค่าแปลภาษา ยังคงโหลดจากการตั้งค่าของ Server แยกจากสถานะการเล่นเสียงปัจจุบัน
