# VoxWeaveTTS

**ทิศทาง Browser-first:** VoxWeaveTTS และ VoxWeaveSTT จะเน้น Core เป็นผู้ทำงานจริง และใช้ Web UI เป็นหน้าควบคุมหลัก พักการพัฒนา VoxWeaveSTT-Client ก่อน โดย STT v0.1.2 รองรับการจัดการ HTTPS LAN ผ่านหน้าเว็บ Local และล็อกอิน Remote Browser ด้วยบัญชีใน .cmd ดู [คู่มือร่วม](docs/BROWSER_FIRST_STT_TTS_TH.md)

**v0.12.15 — แก้ STT API รับข้อความจริง:** แก้การตรวจ session_id ให้ตรงกับ VoxWeaveSTT ที่แยก job session กับ capture session พร้อมคำอธิบาย HTTPS LAN/Fingerprint ที่เข้าใจง่าย ดู [บันทึก Release](docs/RELEASE_NOTES_v0.12.15_TH.md)

**v0.12.14 — VoxWeaveSTT (API):** เพิ่มโหมดรับข้อความที่ถอดเสียงเสร็จจาก VoxWeaveSTT ผ่าน IP/Port ใช้กฎ การแปลและคิวเสียงของ Core เดิม รองรับ HTTPS LAN ที่จับคู่และตรวจ SHA-256 Fingerprint ไม่ต้องอัปเดต STT Core เพื่อใช้งานบนเครื่องเดียวกัน ดู [คู่มือเชื่อมต่อ](docs/STT_API_MODE_TH.md) และ [รายละเอียดรุ่นนี้](docs/RELEASE_NOTES_v0.12.14_TH.md)


**v0.12.13 — Core-first Live Control & Reliable Stop:** การติดตั้งใหม่ใช้ Core รับข้อความ/แปล/สร้างเสียง/เล่นเสียงเป็นค่าเริ่มต้น; Browser ทำหน้าที่ควบคุมและแสดงสถานะล่าสุด รองรับการกด **หยุดเสียงและพักคิว** หรือหยุด Source แยกโหมดจริง มีตัวรับ TikFinity localhost WebSocket ใน Core ที่ไม่ต้องเปิดหน้า Browser ค้างไว้ ขณะที่ YouTube/TikTok DOM ยังต้องใช้ Browser/Extension เป็นตัวจับข้อมูล ดู [คู่มือสถานะ Core ผ่าน Browser](docs/COMPUTER_BROWSER_STATUS_TH.md) และ [คำสั่งหยุด/ตั้งค่า Core](docs/RUNTIME_API_LIVE_TH.md)


**v0.12.12 — ซ่อมเสียงไม่ออกจาก USB DAC และคิวแปล/TTS + ปรับ Web Control ผ่าน LAN** ปรับ Sample Rate, Mono/Stereo และบัฟเฟอร์เสียงได้บน Browser โดย Auto รองรับการแปลงเสียงไปยัง Sample Rate ของอุปกรณ์จริง เพิ่ม Backpressure ลดคิวสะสม และแสดง URL สำหรับเข้า Web Control ชัดเจนแยกจาก Live Listener / Remote Client ดู [รายละเอียด Release v0.12.12](docs/RELEASE_NOTES_v0.12.12_TH.md) และ [โมเดล V4 ทั้ง 7 แพ็กเกจ](https://github.com/funggier/VoxWeaveTTS/releases/tag/v0.12.1-modelpacks-v4)

**แก้ความช้าในการบันทึกโมเดลเสียงตามภาษา (รวมใน v0.12.5):** เดิมปุ่มบันทึกตรวจสอบแพ็กเกจ V4 ซ้ำหลายรอบต่อภาษา แม้ใช้โมเดลเดียวกัน ทำให้เวลาบันทึกเพิ่มตามจำนวนภาษาและจำนวนโมเดลที่ติดตั้ง ตอนนี้เปลี่ยนเป็นตรวจ Manifest ที่ติดตั้งและไฟล์ Worker ด้วยเงื่อนไขความปลอดภัยเดิม **เพียงหนึ่งรอบต่อการบันทึก** ไม่ต้องเริ่มหรือสั่งสถานะ Worker เพียงเพื่อบันทึกโปรไฟล์ ยังคงตรวจใหม่ทุกครั้งที่บันทึก จึงรองรับการติดตั้ง/ถอนโมเดลโดยไม่เก็บแคชสิทธิ์ข้ามคำสั่ง; การบันทึกยังเป็นแบบ revision และเขียนไฟล์อะตอมิกตามเดิม สำหรับเมนู Voice Preset เพิ่มแคชข้อมูล Engine **เฉพาะภายในคำขอโหลดหนึ่งครั้ง** และอ่านไฟล์ JSON แต่ละไฟล์หนึ่งรอบ ลดการสแกนโมเดลที่ซ้ำกัน นอกจากนี้ระหว่างบันทึกหน้า UI จะแสดงข้อความ “กำลังบันทึก…” ทันที และการสร้างเสียงแบบแยกหลายภาษาใช้ Descriptor ซ้ำในงานเสียงเดียวแทนการตรวจใหม่ทุกช่วงภาษา (ความพร้อมของ Worker ยังตรวจตอนสร้างเสียงตามปกติ) ผล Benchmark ภายในบนเครื่องพัฒนา: บันทึก 2 ภาษา จาก 20 ครั้ง/ประมาณ 105 ms เหลือ 1 ครั้ง/ประมาณ 4 ms; ตัวเลขขึ้นกับจำนวนแพ็กเกจและสภาพแวดล้อม

**แถบสถานะด้านล่างของโหมด Live (รวมใน v0.12.4):** แสดงสถานะการเชื่อมต่อและจำนวนที่รับ/กรอง/รอรับจากต้นทาง แยกจากสถานะของระบบอ่านเสียง (กำลังแปล/แยก, เตรียมข้อความแล้ว, กำลังสร้าง WAV, เสียงรอเล่น, กำลังอ่าน, อ่านจบ, พักคิวหรือหยุด) พร้อมจำนวนคิวแชทดิบและจำนวนที่สุ่มลบ · แจ้งข้อผิดพลาดสำคัญแยกแถวเพื่อไม่ให้ข้อมูลใหม่เขียนทับคำเตือน ข้อความสั้น **“กำลังรับข้อความ”** ที่ช่องเชื่อมต่อยังคงอยู่ ไม่ซ้ำในแถบสถานะล่าง

**ปรับปรุง Live Pipeline ใน v0.12.4:** ในทุกโหมด Live สามารถกำหนด **เตรียมข้อความล่วงหน้า 1–100 ข้อความ** และ **เสียงพร้อมรออ่าน 1–20 คิว** แยกกัน (ค่าเดิม 3/2 ตามลำดับ) เพื่อรองรับเครื่องที่มีกำลังประมวลผลสูง ทั้งสองคิวไม่จำเป็นต้องรวมกันไม่เกิน 10 อีกต่อไป มีเพดานหน่วยความจำ WAV รวม 512 MB และงานกลางไม่เกิน 768 รายการ การเพิ่มเพดานไม่รับประกันว่าโมเดลจะสร้างเสียงได้ทันหรือ WAV ทุกไฟล์จะเก็บค้างได้โดยไม่ชนขีดจำกัดอื่น เช่น ขนาด WAV ต่อไฟล์และ TTL งาน

**การอ่านต่อเมื่อเกิดความผิดพลาด:** เปลี่ยนชื่อจากตัวเลือกเดิม และเมื่อเปิด จะข้ามข้อความที่แปล/เตรียม/TTS ไม่สำเร็จ รวมถึงงานที่หมดเวลารอ แล้วอ่านคิวถัดไปอัตโนมัติ (ยกเว้น Browser ปฏิเสธสิทธิ์เล่นเสียงอัตโนมัติ ซึ่งต้องให้ผู้ใช้ปลดบล็อกก่อน) ตั้งเวลา **รอประมวลผลเสียงต่อข้อความ 1–60 นาที (เริ่มต้น 4 นาที)** แยกตามโหมด และเวลาในการรอช่องสร้าง WAV ของงานที่เตรียมเสร็จแล้วจะไม่ถูกนับเป็นเวลาประมวลผล ข้อมูลนี้จะถูกบันทึกในไฟล์ data/settings/source-queues.json โดยเพิ่มค่าใหม่จากรุ่นเก่าอัตโนมัติเมื่ออ่านไฟล์

**บังคับเล่นเสียงต่ออัตโนมัติ (รวมใน v0.12.4):** ตัวเลือกใหม่ที่แยกเปิดปิดในแต่ละโหมด Live และ **ปิดเป็นค่าเริ่มต้น** หาก Browser ปฏิเสธการเล่นเสียงอัตโนมัติ (NotAllowedError / SecurityError) หรือ Browser/คิวแจ้งว่าเริ่มเล่นไม่ได้ ระบบจะข้าม WAV/ข้อความที่เล่นไม่ได้ไปยังข้อความถัดไปโดยอัตโนมัติตาม FIFO โดย **ไม่จำกัดจำนวนข้อความที่ข้ามติดต่อกัน** และแสดงจำนวนข้ามเพราะ Browser บล็อกในแถบสถานะล่าง ถ้า Browser บล็อกทุกข้อความ คิวทั้งหมดอาจถูกข้ามโดยไม่มีเสียงออกมาได้ตามความตั้งใจของผู้ใช้ เมื่อปิดตัวเลือกนี้จะคงพฤติกรรมพักคิวและให้ผู้ใช้แก้ไขสิทธิ์ตามเดิม ตัวเลือกนี้ **ไม่ใช่การปลดล็อกหรือข้ามสิทธิ์ Autoplay ของ Browser** และไม่ส่งผลต่อข้อผิดพลาดแปลภาษา/สร้างเสียง ซึ่งควบคุมด้วย **อ่านต่อเมื่อเกิดความผิดพลาด** แยกต่างหาก การตั้งค่าใหม่บันทึกต่อโหมดโดยไม่เปลี่ยนค่าเก่าจากไฟล์รุ่นก่อน

**Live Pipeline ใน v0.12.3 (เกณฑ์เก่า; รุ่น v0.12.4 ขยายตามด้านบนแล้ว):** เพิ่มสวิตช์ **เตรียมและสร้างเสียงล่วงหน้า** แยกทั้ง 6 โหมด Live โดยกำหนดเพดาน **คิวเตรียม/แปลล่วงหน้า (1–8; เริ่มต้น 3)** และ **คิวเสียงรอเล่น (1–8; เริ่มต้น 2)** ผลรวมไม่เกิน 10 คิว ไม่รวมเสียงที่กำลังเล่นและคิวแชทดิบที่มีระบบสุ่มลดของเดิม เมื่อเปิดระบบจะเตรียมข้อความและสร้างเสียงถัดไปขณะเสียงก่อนเล่นอยู่ แต่ยังเล่นตามลำดับเดิม เมื่อปิดจะกลับไปทำงานแบบเดิม การตั้งค่าแยกแต่ละโหมดและบันทึกได้ ดู [คู่มือและ Release Notes v0.12.3](docs/RELEASE_NOTES_v0.12.3_TH.md)

## Universal v4

ผู้ใช้เพียง **กดติดตั้ง → เลือกไฟล์ .vwmodel → ติดตั้งสำเร็จ** ไม่มีหน้าต่างยืนยันสิทธิ์ซ้ำ และไม่มีการดาวน์โหลด Dependencies ระหว่างติดตั้ง การกดติดตั้งถือเป็นการยอมรับเงื่อนไขของแพ็กเกจและเลือกเชื่อถือ Worker ภายนอกนั้น

- **รองรับเฉพาะ .vwmodel format v4:** ไม่มีตัวอ่าน/ติดตั้ง v1, v2, v3 และไม่มีการเรียก Model Adapter รุ่นเก่าจาก Core
- แพ็กเกจมี Model Weights, Worker Plugin, Configurations, Dependencies และ Metadata สิทธิ์ของตัวเองในไฟล์เดียว
- Python 3.11 Worker พร้อม Wheel ออฟไลน์ หรือ Native Worker แบบโปรแกรม .exe ที่มีสภาพแวดล้อมของตัวเอง
- Engine TTS และ Translation ใช้ Worker Protocol ผ่าน JSON Lines โดย Core จัด Queue, Voice Controls, API และ Subtitle Timeline
- ติดตั้ง/ถอนติดตั้งได้ ไม่ต้องเลือก Python หรือรัน Installer ภายนอก
- เก็บ Settings, Models, Cache และ Runtime ในโฟลเดอร์ Portable โดยรองรับการย้ายตำแหน่งโฟลเดอร์
- ตรวจ ZIP, SHA-256, Safe Paths, Size Limits และ Wheel Startup Hooks อัตโนมัติก่อนติดตั้ง

**ข้อจำกัดความปลอดภัย:** การติดตั้งเป็นการเลือกเชื่อถือโค้ด Engine ซึ่งอาจทำงานด้วยสิทธิ์ Windows ของผู้ใช้ การตรวจ SHA-256 ไม่ใช่การรับประกันความปลอดภัยหรือยืนยันผู้เผยแพร่ และการยอมรับของผู้ใช้ไม่ทดแทนสิทธิ์ที่ผู้แจกจ่ายต้องมีใน Model/Dependencies

## รูปแบบการใช้งาน

- **Document / Narration** — อ่านข้อความและเอกสาร, ปรับความเร็ว/ระดับเสียง, พจนานุกรมการอ่าน และ Preset
- **Discord / YouTube LIVE / TikTok LIVE** — รับข้อความและอ่านตามคิว แยกการตั้งค่าของแต่ละโหมด
- **Translation** — กรองข้อความและแปลข้อความต่างภาษา ก่อนเลือก TTS Model ตามภาษาที่อ่าน
- **Queue / Overlay / API** — คิวเสียงและการอ่านพร้อมข้อมูลเหตุการณ์สำหรับ Subtitle/OBS
- **Global Settings** — กฎการอ่าน, การแทนคำ, Emoji, และการจัดการโมเดล/ส่วนเสริม

โมเดลที่ไม่ได้ติดตั้งจะไม่ถูกเปิดใช้งาน **Core ที่เผยแพร่สาธารณะไม่มีโมเดลเริ่มต้น:** ดาวน์โหลด MakHam, FastThaiG2P, Melo, Supertonic, Kokoro, Wayu และ M2M100 ได้จาก [Release โมเดล V4 ทั้ง 7 ตัว](https://github.com/funggier/VoxWeaveTTS/releases/tag/v0.12.1-modelpacks-v4) ติดตั้งผ่านไฟล์ `.vwmodel` โดยตรง และยังมีแพ็กเกจ Windows SAPI Desktop v4 แยกจาก [v0.12.1](https://github.com/funggier/VoxWeaveTTS/releases/tag/v0.12.1)

### กฎอักษรซ้ำและวลีซ้ำ (รวมใน v0.12.4)

ในแท็บ **กฎการอ่านส่วนกลาง → เพิ่มกฎอย่างรวดเร็ว** เลือก repeat_run สำหรับอักขระหรืออิโมจิที่ติดกัน และ phrase_run สำหรับคำ/วลีที่ซ้ำโดยมีช่องว่างคั่น เช่น หน้าหัวเราะ หน้าหัวเราะ หน้าหัวเราะ ตั้งจำนวนซ้ำขั้นต่ำ (2–1000) ตามแต่ละกฎ หากมีเกณฑ์ 3/5/7 สำหรับตัวเดียวกัน จะใช้เกณฑ์สูงสุดที่เข้าเงื่อนไขและจับทั้งกลุ่มซ้ำ ไม่แบ่งข้อความยาวเป็นกฎสั้นหลายส่วน โหมด phrase_run แบบ replace ที่เว้นช่องคำอ่านแทนว่างจะอ่านวลีแค่หนึ่งครั้งโดยอัตโนมัติ ข้อความ Subtitle ยังแสดงต้นฉบับที่ซ้ำได้ กฎ skip จะไม่อ่านเฉพาะอักขระ/วลีที่ตรงเงื่อนไข การเลือก sources จำกัดกฎเฉพาะช่องทาง เช่น YouTube LIVE ได้ และยังมี five_run ของเดิมเพื่อรองรับกฎ 555 เก่า

ตัวอย่าง: ตั้ง Match เป็น w สามกฎ และ Min Repeats เป็น 3, 5, 7 คำอ่านแทนตามลำดับคือ ฮ่าฮ่าฮ่า / ขำมากมากฮ่าฮ่า / ขำไม่หยุดฮ่าฮ่าฮ่า

### อิโมจิมาตรฐาน YouTube และ Discord (รวมใน v0.12.4)

ระบบมีพจนานุกรมอิโมจิแยกตามแต่ละโหมด Live / YouTube LIVE (Browser) / Discord / Discord Client เปิดใช้งานด้วยตัวเลือก **อ่านอีโมจิด้วยคำที่กำหนดเอง** จากนั้นใส่ อีโมจิหรือชื่อ = คำอ่าน ทีละบรรทัด เช่น 😂 = หัวเราะ, ❤ = หัวใจ, :face-blue-smiling: = ยิ้ม, :yt: = ยูทูบ, :party_parrot: = นกเต้น

- **Unicode มาตรฐาน:** YouTube และ Discord ส่งอิโมจิเป็นข้อความ Unicode ได้ โปรแกรมรองรับทั้งสัญลักษณ์เดี่ยว, emoji+VS16, ลำดับ ZWJ/ธง, และโทนสีผิว เมื่อตั้งฐานอิโมจิไว้จะใช้กับรูปแบบที่ต่างเฉพาะ variation selector และโทนผิวที่ไม่ได้ตั้งชื่อเฉพาะไว้; ค่าเฉพาะที่ระบุจะมีสิทธิ์สูงกว่า
- **YouTube emotes สำเร็จรูป:** โหมด API ใช้ shortcode ที่ได้รับในข้อความ และโหมด Browser อ่านชื่อจาก img.alt ในข้อความ (fallback ไป aria-label หรือ title) โดยปรับชื่ออักษรเล็กที่ไม่มีโคลอน เช่น face-blue-smiling / yt เป็น :face-blue-smiling: / :yt: เพื่อใช้พจนานุกรมชุดเดียวกัน ข้อความต้นฉบับที่เก็บจากโหมดนั้นไม่ถูกเปลี่ยนเป็นไฟล์ภาพหรือโหลดภาพเพิ่ม
- **Discord:** อ่านข้อความ Unicode ตามจริง; custom emoji แบบ <:name:id> และ <a:name:id> จับคู่ชื่อ :name: ได้โดยไม่ต้องระบุ ID หรือกำหนดรหัสเต็มเพื่อให้ตรงเฉพาะรายการ
- **การข้าม/ซ้ำ:** กฎส่วนกลาง skip และ replace ใช้กับข้อความอิโมจิได้ ส่วน repeat_run จัดการอิโมจิที่ติดกันและ phrase_run จัดการอิโมจิหรือคำอ่านซ้ำที่มีช่องว่างคั่น หากเปิดพจนานุกรมแล้ว กฎส่วนกลางจะเห็นข้อความที่แปลงแล้ว เช่น 😂 😂 😂 กลายเป็น หัวเราะ หัวเราะ หัวเราะ
- พจนานุกรมยังจำกัด 64 รายการต่อโหมด และ **ไม่สร้างคำอ่านภาษาไทยอัตโนมัติ** ให้กับอิโมจิที่ยังไม่ระบุชื่อ ไม่รวมอีโมจิที่อยู่ในภาพแนบหรือสติกเกอร์ของ Discord

### อิโมจิ TikTok LIVE (TikFinity และ Extension)

- โหมด TikTok LIVE (TikFinity) ใช้ข้อความคอมเมนต์จาก Local WebSocket โดยตรง ส่วน TikTok LIVE (Extension) อ่านอิโมจิจากภาพเฉพาะในเนื้อหาคอมเมนต์ ไม่อ่านภาพระดับ/เหรียญตราหรือของขวัญ และไม่ดาวน์โหลดภาพ
- อิโมจิ Unicode เช่น 😂 ❤️ 👍🏽 รองรับเช่นเดียวกับ YouTube และ Discord
- อิโมจิพิเศษของ TikTok เมื่อส่งมาเป็นชื่อในวงเล็บเหลี่ยม เช่น [smile], [laughwithtears] และ [cry] สามารถกำหนดในพจนานุกรมของแต่ละโหมดได้ โดยตั้ง [smile] = ยิ้ม หรือ :smile: = ยิ้ม ก็รองรับข้อความ [smile] หากตั้งทั้งสองรูปแบบ กฎ [smile] ที่ตรงตัวจะมีสิทธิ์สูงกว่า
- สำหรับ Extension หากภาพอิโมจิในคอมเมนต์ระบุชื่อ smile ใน alt หรือ aria-label/title จะปรับเป็น [smile] ก่อนเทียบพจนานุกรม แต่ไม่แปลงคำว่า smile ที่ผู้ชมพิมพ์เองเป็นอิโมจิ
